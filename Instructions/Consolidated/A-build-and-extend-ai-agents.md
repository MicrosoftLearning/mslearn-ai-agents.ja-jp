AI エージェントは、生成 AI を使用して要求を理解し、何をすべきかを決定し、ユーザーの代わりにアクションを実行するソフトウェア サービスです。 エージェントを真に有用なものにするのは、モデルだけではありません。それをグラウンディングする**知識**と、付与する**ツール**も必要です。

**シナリオ:** あなたは、製薬会社 **Caldova** で働いており、会社は、前倒しされた製品発売の準備をしているところです。 計画では、3 つの製造サイト全体で 7% のキャパシティ不足が予測されており、各チームは、その不足分を社内で補えるかどうか、そうでなければ事前に適格と認定された契約メーカーを迎え入れられるかどうかを見極める必要があります。 このラボでは、それらの質問に答えるサプライ チェーン アシスタントを構築し、タスクごとに 1 つの機能を追加します。まず、会社のサプライ チェーン ポリシーに基づいてグラウンディングし、その後、ライブ ドキュメントへの接続、生産高の分析し、キャパシティ要求のドラフト作成、材料の在庫確認を行います。

まず、**コア** タスクから始めて、ツールを使用するエージェントを可能な限り迅速に機能できるようにします。 その後、一連の**オプション**のタスクを実行して、最も関心のある分野をさらに詳しく調べることができます。

> **注**: この演習で使用されるテクノロジの一部は、プレビューの段階または開発中の段階です。 予期しない動作、警告、またはエラーが発生する場合があります。

## 学習内容

この演習の**コア** タスクを完了すると、次のことができるようになります。

- エージェントが推測ではなくユーザー独自のデータを基に回答できるように、Microsoft Foundry ポータルで**エージェントを作成し、グラウンディングする**。
- リモートの **モデル コンテキスト プロトコル (MCP)** サーバーに接続し、ツール承認要求をコードで処理して、**ツールでエージェントを拡張する**。

**オプション**のタスクを実行すると、さらに次のことができるようになります。

- **クライアント アプリケーション**からエージェントを呼び出す。
- 独自の Python ロジックを実行する**カスタム関数ツール**をエージェントに付与する。
- **独自の MCP サーバー**を構築して接続する。
- 同じエージェントを構築する 2 つの方法 (**Foundry SDK と Responses API** (自分で作成したもの)) と、**Microsoft Agent Framework** (提供されているすぐに実行できるバリアント) を比較する。
- アシスタントを **ホステッド エージェント** (プロンプト エージェントと同様に参照によって呼び出され、Foundry マネージド コンテナーで実行される独自のコード) としてデプロイする。

2. **任意のタスクを実行する。** 各タスクには必要なセットアップが記載されているため、単独で開始できます。 前のタスクから続けて作業を行う場合、上部の "前のタスクから続ける場合" という**

## 同じエージェントを構築する 2 つの方法

Microsoft Foundry に対してエージェントを記述する方法は複数ありますが、このラボでは、次の **2 つ**の方法を示します。

- **Foundry SDK と Responses API** — このラボ全体で "記述する" アプローチ。**
  `azure-ai-projects` を使用してエージェントを作成し、明示的な JSON スキーマを使用して各ツールを記述し、**ツール呼び出しループを自分で**駆動します (モデルの応答を読み取り、求められたツールを実行し、結果を返します)。 これは、すべてのエージェント ランタイムが内部で実行されるしくみを "確認" できるように、意図的に実践的な内容になっています。**
- **Microsoft Agent Framework (MAF)** — そのプラミングを隠した上位フレームワークです。
  プレーンな Python 関数に `@tool` を修飾し (スキーマが自動的に生成されます)、`await agent.run(...)` を呼び出します。これにより、ツール呼び出しループ全体が自動的に実行されます。

これらは、どちらかが "より正しい" というわけではなく、抽象化のレベルが異なります。 最初に生のしくみを確認すると、フレームワークのショートカットが後で意味を持つようになります。 その対比を具体的に示すために、**タスク 4 と 5 ではそれぞれ、同じアシスタントのすぐに実行できる MAF エディション** (`functions_agent_maf.py` と `client_maf.py`) が提供されており、それらを読んで実行し、自身のバージョンと比較することができます。 Microsoft Agent Framework については、「**ラボ 07 (Agent Framework)**」および「**ラボ 08 (マルチエージェント オーケストレーション)**」で詳細に説明します。

## まとめ

このラボでは、次の作業を行いました。

- Foundry ポータルでエージェントを作成して**グラウンディング** し、エージェントが自分のデータを基に回答するようにしました。
- エージェントをリモート MCP サーバーに接続し、ツール承認要求をコードで処理して、**ツールを使用してエージェントを拡張**しました。
- (省略可能) **クライアント アプリ**からエージェントを使用し、**カスタム関数ツール**を追加し、**独自の MCP サーバー**を構築しました。その後、関数ツールと MCP ツールを、呼び出しを適切な場所にルーティングする 1 つの**キャップストーン アシスタント**に統合しました。
- (省略可能) アシスタントを**ホステッド エージェント**に昇格しました。これにより、独自のコードが Foundry マネージド コンテナーにデプロイされ、参照で呼び出されるようになりました。

これらを合わせると、エージェントを有用なものにするための 2 つの大きな方策が明らかになります。つまり、適切な**知識** (グラウンディング) と適切な**機能** (ツール) をエージェントに付与することです。

## クリーンアップ

完了したら、不要な Azure コストを回避するために、作成したリソースを削除します。

1. [Azure portal](https://portal.azure.com) で、Foundry リソースが含まれているリソース グループに移動します。
1. ツール バーで、**[リソース グループの削除]** を選択してリソース グループの名前を入力し、確認します。

> タスク 2 で実行したコードで作成されたエージェント バージョンは、そのコードによって既に削除されています。 ポータル エージェントは、リソース グループを削除すると削除されます。 `azd` を使用してプロビジョニングした場合は、代わりに `azd down` を実行すると、作成したすべてのものが削除されます。
